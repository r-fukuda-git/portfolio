
# golang
- r.ParseForm() とは
  - Go言語のnet/httpパッケージにおいて、HTTPリクエストのボディ（POSTデータ）とURLクエリパラメータを解析し、r.Formフィールドにデータを格納するメソッドです。
  - 基本フォームの解析を実施し、その後、r.Formを用いてデータの取得を実施する
- interface{} は「どんな種類のものでも入れられる魔法の箱」を意味
  - インターフェースは「この箱に入るには、こういう機能（メソッド）を持っていないとダメ」という条件を書きます。しかし {}（中身が空っぽ）と書くことで、「何の条件もない＝何でも入る」という意味
  - Goのバージョン1.18以降では、この interface{} を短く書ける any というキーワードが追加されました。実務では var args []any と書くのが今の主流です。
- db.Exec の可変長引数が any を要求するため、動的に値を渡すにはスライスも any 型で宣言する必要がある
  - args... のようにドットを3つ書くと、配列の中身を展開して渡せます
  - 数がわからない、把握できないためドットを記載して箱から取り出せる
  - db.Exec という関数は、ある時はID（数字）を受け取りますが、別の機会ではタイトル（文字）やステータス（真偽値）も受け取ります。
  - db.Exec を作った人は「この関数にはどんな種類（型）のデータが来るかわからないから、とりあえず何でも入る魔法の箱（any）で渡してね」というルール
  - 全てはGoの型が厳しいため

# PrintfやSprintfのケースのまとめ
- %v (Value - デフォルト)
- %s (String - 文字列)
- %d (Decimal - 10進数)
- %t 論理値（bool）をtrueまたはfalseで出力する。
- %f 浮動小数点数（float）を固定精度で出力する。
- %q 文字列をダブルクォーテーションで囲んで出力する（"string"）。
- %x 16進数（小文字）で出力する。
- %T 値の型（type）を出力する。

# SQLについて
- SQLの文法の違い: データを追加する INSERT INTO の場合は、どのカラムに値を入れるか指定するために tasks (title, completed, ...) のようにカッコを使います。
- DELETEの正しい形: 一方、データを削除する DELETE FROM の場合は「行そのもの」を削除するため、テーブル名の直後に (id) のようにカラム名を指定する必要はありません。「どのテーブルから」「どの条件（WHERE）で」削除するかだけを指定します。
- 一括削除の考慮点
  - トランザクションの制約の考慮が必要
    - 3件選択して2件までしか削除できないケースなど全然ありうるため、全部実施するか、失敗するかの処理が必要
  - ループ処理で1個ずつDELETEは非効率
    - 1回のSQLでまとめて削除する工夫が必要になる
- 実務でよく使われる WHERE 1=1（常に正しい条件）から始めると、後から AND で条件を付け足しやすくなります。

# 文法について
:= （宣言と代入）: 初めて変数の箱を作って、中身を入れる時に使います（例: query := "SELECT..."）。
== （比較）: 左右の値が「同じかどうか」を判定します。if 文の中で使います。
+= （追加・結合）: 今ある箱の中身に、新しいものを付け足して上書きするという意味です。文字列の場合、「文字を後ろにくっつける」という動きになります。query = query + " AND ..." と書くのと同じですが、+= の方が短くて便利なのでよく使われます。

# ログインページについて
- 合言葉の登録（サインアップ）: 自分の名前と、秘密の合言葉（パスワード）を登録します。このとき、合言葉そのものをDBに保存してはいけません。
- 合言葉の確認（ログイン）: 合言葉が合っていれば、サーバーから「会員証（セッションやクッキー）」を渡されます。
- 会員証の提示（リクエストごと）: ページを移動するたびに、ブラウザはこの「会員証」を自動的にサーバーに見せます。サーバーはそれを見て「あ、君はA君だね」と判断します。
- 本人専用のデータ表示: A君にはA君が作ったタスクだけを見せ、B君のものは隠します。

- パスワードを平文（そのまま）で保存せず、bcryptでハッシュ化した
- ユーザー認証における「クッキーからの取得」と「未ログイン判定」


# セッションとクッキーの違いってなに？
クッキー（Cookie）：
    場所：ユーザーのブラウザに保存されます。
    役割：サーバーからもらった「引換券（セッションID）」を大事に持っておくポケットのようなものです。

セッション（Session）：
    場所：サーバー側のメモリやデータベースに保存されます。
    役割：ユーザーごとの「本棚」です。本棚にはユーザーID、名前、権限などの大切な情報が入っています。

- サーバーは推測不可能なランダムな文字列（セッションID）を発行し、「このIDを持ってきた人はユーザーID 1番の人だ」とサーバー側で紐付けて管理します。

- セッションハイジャック対策の知識: 実務では、クッキーに直接 1 などのユーザーIDを書き込むことはしません（悪意のあるユーザーが 2 に書き換えて他人のデータを盗めてしまうため）。代わりに、推測不可能なデタラメな文字列（セッションIDやトークン）を発行してクッキーに持たせます。この「なぜ直接IDを入れないのか？」を説明できると、セキュリティへの理解度がアピールできます。

# ログイン処理の流れ
- ユーザー検索を実施して、DBにパスワードが存在するか
- 存在するのであれば、入力されたパスワードとDBのハッシュを一致させる
- 成功すれば、ブラウザにセッション情報を持たせる
- 失敗すれば、ブラウザに失敗と表示
- HttpOnly属性の指定: 「XSS（クロスサイトスクリプティング）対策として、JavaScriptからクッキーを読み取れないように HttpOnly 属性を付与しています」と言えることは、Webセキュリティの基本を押さえている証拠です。
