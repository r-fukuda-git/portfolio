# エラーハンドリング
- ユーザーの誤操作（何も選択せずに送信など）を想定し、DBへの無駄なクエリを発行する前に len() を用いて nil と空スライスの両方を安全にハンドリングするガード節（早期リターン）を実装

# ゼロ値の考え方
- int（数字）のゼロ値は 0 です。
- string（文字）のゼロ値は ""（空文字）です。

# contextってなに？
- Webアプリには、同時にたくさんのユーザーがアクセスしてきます。
- Go言語のルールでは、リクエスト（r）がサーバーに届いた瞬間、ユーザー一人ひとりに**「その人専用の見えないリュックサック（Context）」**を背負わせます。
- context.WithValue(リュック, 名札, 中身)
  - そのリュックの中に、「"user_id" という名札」をつけた「実際のID番号（例：5）」を入れます。
- r.WithContext(ctx): ユーザーのリクエスト（r）に、先ほど作った「証明書入りの新しいリュック（ctx）」を背負い直させます。

# 別パッケージの型にメソッドを作成するのは禁止
- 別パッケージに持ってくるならDI(依存性の注入)を作成する
- Go言語において、パッケージ名（handlers）は**名前空間（Namespace）**としての役割を持ちます。
- 構造体の変数（myTasks）からドット . で繋いで呼び出せるのは、その構造体が持っている**フィールド（プロパティ）か、その構造体をレシーバー（Receiver）**として定義されたメソッドだけです。パッケージをまたいでチェーン（連結）させることは言語仕様上できません。

# マルチモジュール
- プロジェクトの一番上のフォルダ（todo/）にだけ、新しく go.mod を作ります（go mod init todo）。
- もしくは下記の手段を実施する
- go work init ./cmd ./handlers ./common ./models

# ビルド
- Go言語のコンパイラに対して go build A.go B.go C.go のようにファイルを複数直接指定する書き方は、「これらすべてのファイルをガッチャンコして、1つの同じパッケージとしてビルドしてね」という指示になります。
- そのため、Go言語は「cmd/main.go と common/common.go は別のフォルダ（別の村）なのに、一緒にしろって言われても無理だよ！」とパニックを起こしてしまったのです。
- 他のフォルダにあるgoファイルは指定しなくてもまとめて対応してくれる

# SQLクエリ
- プレースホルダー（$1）を使用したSQLクエリにおいて、実行時のバインド変数の渡し忘れによる実行時エラー（Runtime Error）が発生しました
- どうやってミスを防ぐのか？
  - ① ORM（オーアールエム）やクエリビルダーを使う
    - 生のSQLを書く代わりに、GORM や sqlx などの外部ツールを使います。これらを使うと、Go言語が変数の数を自動で合わせてくれるため、渡し忘れが原理的に起こらなくなります。
  - ② sqlc などのコード自動生成ツールを使う（最近のトレンド）
    - SQL文を書くと、それを読み取って「引数が2つ必要なGo言語の関数」を自動で作ってくれる強力なツールです。これなら渡し忘れるとコンパイルエラーになるので安全です。
