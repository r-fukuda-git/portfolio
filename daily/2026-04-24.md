# golang/todoについての現状の問題点
## セッション管理の脆弱性（セキュリティ）
- 事実: 現在、ログイン時に発行する Cookie の session_id に、入力された username をそのまま保存しています。
- 課題: これでは、ブラウザの開発者ツールから Cookie の値を他人のユーザー名に書き換えるだけで、簡単にその人に「なりすまし」ができてしまいます。
- アピールポイント: ここを「ランダムで推測不可能なトークン」を使ったセッション管理に改修することで、「Webセキュリティの基本を理解し、安全な設計ができるエンジニア」としてアピールできます。

- math/rand は「サイコロの出目の順番が書かれた本」です。最初はランダムに見えますが、どのページから読み始めたか（シード値）がバレると、次に出る数字が完全に予測されてしまいます。
- crypto/rand は「風の吹き方や温度の変化などを読み取って作る、本物のサイコロ」です。次に何が出るか、コンピュータ自身にも予測できません。セキュリティには必ずこちらを使います。

- QueryRow と Exec の違い
  - Exec:用途: INSERT (追加)、UPDATE (更新)、DELETE (削除)
    - 「この書類、キャビネットにしまっといて！（または捨てておいて！）」という命令です。「はい、やりました！」という結果（エラーがなかったか）だけ分かれば良いので、データを受け取る機能（Scan）は付いていません。
  - QueryRow (Query = 質問する, Row = 1行)
    - SELECT (検索) で、絶対に1件（または0件）しか結果が返ってこないと分かっている場合。

- ゲスト用のセッションIDも発行しておき、ログインしたらそのセッションIDにするということもやりたい
  - 現実はセッションIDをDBに保存している場合、未ログインユーザー分も発行するとなると、ディスク枯渇か、パフォーマンス低下につながる
  - なので、有効期限付きのRedisを導入することで解消する

## 運用を見据えたログ設計（オブザーバビリティ）
- 事実: fmt.Println と log.Println が混在しており、単なる文字列として出力されています。
- 課題: トラフィックが多いメガベンチャーの実務では、この形式だと「誰が、いつ、どこで、何のエラーを起こしたか」をログ監視ツール（Datadogなど）で検索・集計することが困難です。
- アピールポイント: インフラエンジニアの強みを活かし、検索しやすい「構造化ログ（JSON形式などのログ）」を導入することで、「障害発生時に迅速に原因特定ができる、運用しやすいシステムを作れる（SRE的思考）」とアピールできます。

## 構造体への直接依存（Go Idiomatic / 設計）
- 事実: handlers.TaskHandler が *models.TaskList という「具体的な構造体」に直接依存しています。
- 課題: これが「Bash的な順次処理」の延長にある書き方です。このままだと、テスト時に「本物のDB」がないとハンドラーのテストができず、自動テストが難しくなります。
- アピールポイント: インターフェースを用いた「依存性の注入（DI）」というGo言語らしい設計手法を取り入れることで、「拡張性が高く、テストが容易な設計ができる」と大きく評価されます。
